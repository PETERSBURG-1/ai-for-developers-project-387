# Календарь звонков (продолжение)

[![hexlet-check](https://github.com/PETERSBURG-1/ai-for-developers-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/PETERSBURG-1/ai-for-developers-project-387/actions)

Сервис записи на звонок по мотивам Cal.com. Владелец календаря один и задан заранее:
он создаёт типы встреч и смотрит предстоящие записи. Гость без регистрации выбирает
тип встречи, свободный слот в ближайшие 14 дней и записывается на звонок.

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Референс Cal.com

Изучен пользовательский путь Cal.com: владелец создаёт тип события (название,
описание, длительность, доступность) и делится ссылкой; гость открывает календарь,
выбирает дату и время, заполняет имя, email и заметки, подтверждает бронь; слот
исчезает из свободных, а запись появляется в списке владельца. Пересечения с уже
существующими встречами блокируются.

В нашем приложении сохраняем только этот базовый сценарий. За рамками: регистрация,
личные кабинеты, внешние календари, уведомления, видеоконференции, оплата, переносы
и отмены.

## Сценарий владельца

1. Владелец открывает раздел «Админка» — видит типы встреч и список предстоящих
   записей всех типов, отсортированный по времени начала.
2. Создаёт тип «Встреча 15 минут»: название, описание «Короткий тип события для
   быстрого слота», длительность 15 минут. Тип сразу появляется в каталоге для гостя.
3. При необходимости создаёт второй тип, например «Встреча 30 минут».
4. Когда гость записывается, в списке предстоящих появляется запись: дата и время,
   тип встречи, имя и email гостя, заметки.

## Сценарий гостя

1. Гость открывает главную страницу и нажимает «Записаться».
2. В каталоге выбирает тип события — карточка открывает календарь.
3. В календаре доступны 14 календарных дней, начиная с завтрашнего; окно скользящее.
   У каждого доступного дня показано количество свободных слотов для выбранного типа.
4. Гость выбирает день и свободное время. Рабочий день — 09:00–18:00 (Europe/Moscow),
   слот длится столько же, сколько тип встречи, старты идут с тем же шагом. Занятые
   слоты видны, но недоступны.
5. Нажимает «Продолжить», указывает имя, email и заметку, подтверждает бронирование.
6. Видит подтверждение: тип встречи, дата, время. Слот становится занятым, счётчик
   свободных слотов дня уменьшается. Эта же запись появляется у владельца в «Админке».

## Обязательные функции

- Каталог типов встреч с названием, описанием и длительностью.
- Админка: создание, редактирование и удаление типов; список предстоящих записей
  всех типов.
- Календарь на 14 дней и список слотов выбранного дня.
- Бронирование гостем без регистрации: имя, email, заметки.
- Запрет пересечений любых типов встреч, включая частичные; смежные интервалы
  разрешены (конец одной встречи может совпадать с началом следующей).
- Атомарная проверка занятости: два одновременных запроса не могут занять одно время.

## Ограничения

- Один владелец, задан заранее; авторизации и личных кабинетов нет.
- Нет интеграций с внешними календарями, уведомлений, видеозвонков и оплаты.
- Окно записи — 14 календарных дней, начиная с завтрашнего дня.
- Рабочие часы — 09:00–18:00 ежедневно, часовой пояс Europe/Moscow.
- Длительность слота равна длительности типа, шаг доступных стартов — тоже.
- Приложение собирается в Docker-образ и запускается в контейнере.
- Хранение — в памяти процесса: после перезапуска сервиса записи и созданные типы
  сбрасываются. (Уточняется на шаге выбора стека; при переходе на БД пункт обновим.)

## Генерация клиента

- Контракт API описывается на TypeSpec; из него генерируется OpenAPI 3.1.
- Для фронтенда генерируется клиентский SDK из OpenAPI; генератор проверяется
  до выбора стека.
- Серверные типы и маршруты генерируются, если выбранный фреймворк это поддерживает;
  иначе сервер реализуется по контракту и проверяется тестами.

## Стек

- TypeScript, Node.js 24, pnpm 12.
- Контракт: TypeSpec 1.18 → OpenAPI 3.1.
- Клиент и схемы: `@hey-api/openapi-ts` (SDK, типы, Zod).
- Бекенд: Fastify 5 + Zod.
- Фронтенд: Vite 8, React 19, Tailwind CSS 4, shadcn/ui.
- Тесты: Vitest. Линтер и форматтер: Oxlint + Oxfmt.
- Окружение и задачи: mise, pitchfork (daemons), hk (Git-хуки).
- Контейнер: Docker, один образ с API и собранным фронтендом.

## Установка

Установите [mise](https://mise.jdx.dev/installing-mise.html), затем:

```bash
git clone https://github.com/PETERSBURG-1/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise install
mise run setup
mise run setup:e2e
mise exec -- hk install --mise
```

`mise install` ставит зафиксированные версии Node.js, pnpm и инструментов проверок.
`mise run setup` устанавливает зависимости, `setup:e2e` — Chromium для Playwright,
`hk install` — Git-хуки.

## Использование

```bash
mise run dev
```

- Приложение: http://localhost:5173
- API: http://localhost:3000/api/health

Dev-серверы работают как daemons mise:

```bash
mise daemons status
mise daemons logs
mise daemons stop
```

Проверки:

```bash
mise run check
```

Команда запускает генерацию контракта, линтер, проверку типов, тесты, сборку
и браузерный E2E с реальными API и web. Она же используется в GitHub Actions.

Docker:

```bash
mise run docker:build
mise run docker:run
```

Контейнер слушает `PORT` (по умолчанию 3000) и раздаёт собранный фронтенд и API.
Для нестандартного порта:

```bash
docker run --rm -e PORT=10000 -p 10000:10000 calendar:local
```

## GitHub-агент

В репозитории используется GitHub App [OpenCode Agent](https://github.com/apps/opencode-agent)
и воркфлоу `.github/workflows/opencode.yml`. Ключ модели хранится только в
GitHub Secrets под именем `OPENCODE_API_KEY`.

Воркфлоу запускается по комментариям:

- `issue_comment` с типом `created` — обсуждение issue или PR;
- `pull_request_review_comment` с типом `created` — комментарий к строке diff.

Команды вызова — `/oc` и `/opencode` (стандартный набор `mentions`). Работать
может только автор с ролью `OWNER`, `MEMBER` или `COLLABORATOR`; комментарии
ботов игнорируются. Модель — `opencode/deepseek-v4.1-flash`.

Агент объясняет issue, помогает с реализацией, вносит правки в PR и разбирает
строки diff. Ответ появляется комментарием в issue или PR, изменения — в
ветке и PR. Прогон и логи доступны в Actions, workflow `opencode`.

Права задания: `contents: read`, `id-token: write` и `issues: write` для
`gh`-команд скиллов; checkout выполняется с `persist-credentials: false`.
`GH_TOKEN` берётся из `GITHUB_TOKEN` задания, остальные действия агента идут
токеном OpenCode App. Таймаут
задания — 30 минут, параллельные запуски ограничены номером issue или PR.
Сессии не публикуются (`share: false`). Перед запуском на чистом раннере
воркфлоу копирует проектные скиллы из `.agents/skills` в `.opencode/skills`;
настройки трекера берутся из `docs/agents/`, команды — из `AGENTS.md`.

Для запуска добавьте ключ OpenCode в Settings → Secrets and variables → Actions
под именем `OPENCODE_API_KEY` и установите приложение на репозиторий.

### Автотриаж

Новые обращения разбирает отдельный воркфлоу `.github/workflows/opencode-triage.yml`.
Он запускается по событию `issues` с типом `opened` и передаёт агенту prompt,
который вызывает скилл `triage`: агент читает `docs/agents/issue-tracker.md`,
`docs/agents/triage-labels.md` и `AGENTS.md`, проверяет текущее поведение
приложения, ставит категорию и состояние и оставляет комментарий с конкретными
вопросами или agent brief. Спецификацию, тикеты, код и PR он не создаёт.

Запуск ограничен доверенными авторами с ролью `OWNER`, `MEMBER` или
`COLLABORATOR`; issues от ботов не разбираются. Обращения с метками
`ready-for-agent` и `wayfinder:task` пропускаются — они уже подготовлены.

Модель — `opencode/deepseek-v4.1-flash`, таймаут задания — 20 минут,
параллельные запуски ограничены номером issue (одна очередь на issue).
Права задания: `contents: read`, `id-token: write` и `issues: write` для
`gh`-команд скилла; `GH_TOKEN` берётся из `GITHUB_TOKEN` задания. Результат —
комментарий в issue, а прогон и логи доступны в Actions, workflow
`opencode-triage`.

### Авторевью PR

Независимое авторевью запускает `.github/workflows/opencode-review.yml` на
событии `pull_request`: `opened`, `synchronize`, `reopened`, `ready_for_review`.
Оно работает с точным `head.sha` PR, только для веток этого репозитория и
доверенных авторов; PR от `opencode-agent[bot]` разрешён, PR из fork пропускаются
без секретов. Используется обычный OpenCode CLI в read-only режиме, отдельный шаг
публикует результат через `gh pr comment`.

Критерии ревью лежат в `REVIEW.md` и передаются агенту в prompt. Агент читает
описание PR, спецификацию, тикеты, согласование, diff и статусы CI. Определение
workflow и `REVIEW.md` берутся из base; код PR не исполняется, diff читается
через `gh`. Агент ревью работает с read-only токеном: `contents: read`,
`issues: read`, `actions: read`, `checks: read`, `statuses: read`,
`pull-requests: read`. Публикация — отдельное задание с `pull-requests: write`.
Таймаут — 20 минут, concurrency отменяет устаревшее ревью того же PR.
Авторевью не меняет код.

### Бюджет запусков на PR

Интерактивный workflow `opencode` разрешает не больше трёх запросов `/oc` на
один PR. Попытки считаются по истории Actions и `run_attempt` до вызова модели;
комментарий PR не является источником бюджета. Исчерпание публикует отдельный
комментарий с причиной `limit_exhausted`, последним SHA и ссылкой на лог. Для отмены или таймаута
отдельное задание публикует `timeout_or_cancelled`, для сбоя агента —
`agent_failed`; следующее действие выбирает человек.

### Шаблон PR и браузерная проверка

`.github/pull_request_template.md` требует заполнить проверки, риск и способ
отката. На PR отдельное задание `browser` в CI переключается на точный
`pull_request.head.sha`, записывает фактический `git rev-parse HEAD` и запускает
Playwright с включённым trace. Артефакт `playwright-<sha>` содержит trace/report,
результат и SHA; перед мержем человек сверяет SHA с текущим head PR.

### Аудит по расписанию

Ежедневный Lighthouse-аудит запускает `.github/workflows/opencode-audit.yml`:
`schedule` с cron `17 3 * * *` (06:17 МСК) и `workflow_dispatch`. Задание имеет
`timeout-minutes: 30`; параллельные аудиты ограничены `concurrency`.

Адрес приложения задаётся repository variable `APP_URL`; журнал аудита —
`AUDIT_LOG_ISSUE` (issue #19). Сырой Lighthouse-отчёт сохраняется artifact
`audit-report-<run_id>-<run_attempt>`, итог агента — отдельный
`audit-output-<run_id>-<run_attempt>`; оба хранятся 30 дней. Агент анализирует
отчёт, ищет существующие задачи по маркеру `audit-key` в теле issues и создаёт
новый issue только по новой находке. При отсутствии находок или дубле он
пишет результат в журнал аудита. Учебная находка передаётся через
`workflow_dispatch` inputs `demo_finding`/`demo_key`, помечается label
`training` и не считается подтверждённым дефектом. `.audit/` исключён из Git.

### Деплой

Проектная конфигурация MCP находится в `opencode.json`: сервер Railway
`https://mcp.railway.app/mcp` с OAuth. Порядок подключения:

1. Откройте OpenCode и выполните `/mcps`, выберите `railway` и пройдите OAuth.
   Данные сессии хранятся вне репозитория.
2. Создайте проект и сервис из GitHub-репозитория; Railway собирает `Dockerfile`
   и запускает контейнер с переменной `PORT`.
3. Если в вашей сети `mcp.railway.com` или `backboard.railway.com` недоступны,
   используйте alias `mcp.railway.app` и `backboard.railway.app`.
4. Для неинтерактивного CLI-деплоя можно экспортировать `RAILWAY_TOKEN`
   (см. `.env.example`). Реальный токен в Git не добавляйте.

Данные хранятся в памяти процесса: после перезапуска контейнера, сервиса или
редеплоя созданные типы встреч и записи сбрасываются.

Подробности — в [CONTRIBUTING.md](CONTRIBUTING.md) и [AGENTS.md](AGENTS.md).
